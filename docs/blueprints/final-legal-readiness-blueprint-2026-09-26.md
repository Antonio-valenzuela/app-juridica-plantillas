> Generated by The Architect on 2026-09-26

## 1. Project Overview

### Vision

APP-plantillas is a local and web-ready legal drafting tool for one lawyer: the user's father. It accepts real case documents, extracts and classifies their contents, builds a traceable legal document plan, generates a draft through the existing legal pipeline, validates the result, and exports the same document to DOCX and PDF for human review.

The first release is intentionally a single-user system. It keeps the current Prisma persistence, upload analysis, generation jobs, legal templates, editor, export guards, DOCX renderer, and PDF renderer. It does not add organizations, billing, collaboration, multi-user permissions, or a Windows installer in this phase. Internal identifiers and organization fields remain available so a later multi-user version can be added without redesigning the legal domain model.

### Goals

- Execute six genuinely different real cases from `C:\Users\yahir\Desktop\Datos.zip` through the complete source-to-export pipeline.
- Produce one matching DOCX and PDF pair for each approved case, with the same factual content and traceable source metadata.
- Prevent invented names, dates, parties, authorities, facts, legal citations, precedents, or procedural acts.
- Allow `REQUIERE_REVISIÓN` drafts when essential information is missing while blocking a misleading `FINAL` export.
- Compare generated documents against the supplied Galarza Meza DOCX references for hierarchy, prose, layout, and professional presentation.
- Preserve useful PowerShell evidence: stage duration, provider/model, requests, errors, warnings, retries, semantic status, byte lengths, and output paths.
- Leave the current web/local app stable and documented for a later Windows packaging phase.

### Success Metrics

- Six distinct cases have complete E2E evidence from source loading through DOCX and PDF export.
- Each approved case passes factual, legal, procedural, prose, structure, DOCX, PDF, and visual gates.
- A case with essential missing data is visibly `REQUIERE_REVISIÓN`; it cannot be presented as `FINAL`.
- No generated output contains Markdown, JSON, pipeline logs, technical blocks, unsupported placeholders, or unexplained characters.
- `npm run typecheck`, `npm run lint`, relevant Vitest suites, E2E validation, and `npm run build` have recorded results.
- Every limitation that remains unresolved is named as a blocker or risk instead of being hidden by a green transport status.

## 4. Data Model

The current Prisma schema is the source of truth. No schema replacement is part of this blueprint.

### Existing entities used by the audit

**Organization**

The current single-user deployment keeps one organization scope for isolation and future expansion. It is not exposed as a multi-tenant feature in this phase.

**User**

The current user record identifies the single lawyer/operator. Do not add teams, invitations, role management, or account administration now.

**LegalDraft**

Stores `title`, `documentType`, `matter`, `jurisdiction`, form data, rendered text, pending markers, `structuredDoc`, `pipelineState`, source documents, validation results, generation metadata, and status. This is the durable document record.

**GenerationJob**

Stores job identity, organization/user scope, document ID, fingerprint, idempotency key, phase, progress, terminal status, cancellation state, warnings, and errors. A terminal job must not later be reported as processing or successfully completed with contradictory state.

**CaseParty**

Stores party role, name, source, confidence, case key, organization scope, and optional draft relation. Manual confirmed parties outrank detected or inferred parties.

**LawyerStyleProfile**

Stores the one lawyer's preferred tone, structure, ordering, recurring formulas, citation style, terminology, defense phrasing, and document-length preferences. The profile may influence expression but cannot override factual or legal gates.

**AiUsageLog / AiUsageEvent**

Store provider/model, operation, status, fallback, duration, token/cost metadata, request ID, route, mode, errors, and latency. These records support the PowerShell timing report and slow-process investigation without storing API keys.

### Audit-only entities and files

The six cases are stored in `audit/final-legal-readiness-2026/cases/NN/`, not in the production database as permanent seed data. The runner may persist derived metadata and generated artifacts in the audit tree, but the source ZIP must never be copied into the production upload directory or treated as a database.

### Required per-case manifest

```json
{
  "caseNumber": "01",
  "sourceRelativePath": "Datos/...",
  "sourceSha256": "...",
  "sourceBytes": 0,
  "sourceMime": "application/pdf",
  "selectedDocumentType": "...",
  "workflow": "DOCUMENT_ANALYSIS",
  "sourceValidated": false,
  "readiness": "REQUIRES_REVIEW",
  "qualityGate": "FAIL",
  "stages": [],
  "providerAttempts": [],
  "outputs": {
    "docx": null,
    "pdf": null
  }
}
```

The manifest is evidence, not a second source of legal facts. Its fields must be populated from API responses and generated trace data, never from guessed values.

## 5. API and Pipeline Contracts

| Method | Path | Purpose | Required state |
|---|---|---|---|
| POST | `/api/templates/analyze-upload` | Extract, classify, score, and optionally start async analysis. | Source bytes and supported type. |
| GET | `/api/templates/analyze-upload/status` | Poll upload/OCR analysis. | Job ID. |
| POST | `/api/templates/analyze-upload/cancel` | Cancel background analysis. | Job ID and ownership. |
| POST | `/api/legal-engine/generate` | Create an idempotent generation job. | Valid source for `DOCUMENT_ANALYSIS`; explicit Flow B for new writing. |
| GET | `/api/legal-engine/generate/status` | Poll generation and recover terminal document state. | Job ID. |
| POST | `/api/legal-engine/generate/cancel` | Request cancellation. | Job ID. |
| GET/POST | `/api/legal-drafts/[id]` | Load/update persisted draft state. | Draft ID and local identity. |
| POST | `/api/legal-engine/review` | Run review/validation contract. | Structured document and source trace. |
| POST | `/api/legal-engine/export/docx` | Prepare, validate, materialize, and return DOCX. | `DRAFT` or verified final mode; FINAL requires readiness gates. |
| POST | `/api/legal-engine/export/pdf` | Prepare, validate, render, and return PDF. | Same guard contract as DOCX. |

### Pipeline stages

Every real case must emit observable evidence for:

1. source selection and SHA-256;
2. upload request/response;
3. extraction and page count;
4. OCR decision and page progress, if applicable;
5. classification;
6. case analysis and source quality;
7. generation context and page-aware source references;
8. document type and procedural identity;
9. section/block plan;
10. provider calls, fallbacks, retries, and durations;
11. semantic validation and quality/readiness state;
12. document assembly;
13. review output;
14. DOCX binary export and manifest;
15. PDF binary export and page markers;
16. visual render inspection and final case verdict.

### State rules

- `sourceValidated=false` blocks source-based generation unless an explicit review mode exists and the warning is visible.
- `REQUIRES_REVIEW` may produce a marked draft for a lawyer but cannot be silently upgraded to `FINAL`.
- `VALID_NON_FINAL` is not substantive approval.
- `qualityGate=FAIL`, unresolved essential facts, unsupported legal citations, missing client position, or failed structural validation block final export.
- A PDF or DOCX HTTP 200 response is not proof of substantive correctness.
- A provider health response is not proof of persistence, generation completion, or exportability.
- All model-proposed authorities must be allowlisted against verified source data or official research evidence.

The UI should remain a dense desktop legal tool, not a consumer dashboard. The supplied DOCX references control legal-document typography; the app interface should support that workflow without copying their case facts.

### Colors

| Deep ink | `#0B1F33` | High-contrast text and document metadata. |
| Amber accent | `#C58A2A` | Review markers, attention states, active borders, and limited emphasis. |
| Background | `#F5F7FA` | Workspace background. |

| Warning | `#9A6700` | `REQUIERE_REVISIÓN`, unresolved source, or pending human decision. |
| Success | `#137333` | Verified stage completion only. |

### Typography and layout

- App UI: a readable system sans family with 14–16px body text and compact 20–28px headings.
- Generated legal documents: preserve the selected reference-derived style and the actual export page profile; do not use app UI fonts as document defaults without evidence.
- Desktop-first working widths: optimize 1366×768, 1440×900, and 1920×1080.
- Contestaciones layout target: approximately 60% document viewer and 40% right review panel, subject to existing components and evidence.
- Spacing: 4/8px rhythm; compact cards; enough whitespace to separate legal states without creating empty dashboards.
- Interaction: visible keyboard focus, disabled states, loading feedback, and errors next to the action that failed.
- Accessibility: do not rely on color alone; use text/status labels for `PASS`, `REQUIERE_REVISIÓN`, `FAIL`, and `BLOQUEADO`.

### Document visual contract

The two supplied references are benchmarks, not content sources. Audit their actual margins, headers/footers, typeface, title hierarchy, spacing, numbering, section density, signature blocks, and page rhythm. Generated output must use a stable, source-derived document profile and must be rendered before acceptance. A missing renderer is a blocker, not a reason to waive visual QA.

## 9. Audit Build Order

This is the execution order for the current working tree. It is an audit-and-repair plan, not a Windows packaging plan.

1. **Freeze the baseline.** Record Git status, current branch, Node/npm versions, environment key presence without values, Prisma connectivity status, and existing test/build baselines. Do not commit or push.
2. **Inventory the six inputs without extracting the entire ZIP.** Enumerate candidate files from the ZIP central directory, classify by extension and likely case family, select six genuinely different cases, and record the selection rationale.
3. **Distill the DOCX references.** Preserve both reference files byte-for-byte; capture hashes, section/page geometry, styles, headings, headers/footers, tables, markers, and visual-render availability.
4. **Map the real pipeline.** Verify source upload, async analysis, classification, context, plan, generation, validation, assembly, editor, DOCX export, and PDF export against current files and CodeGraph.
5. **Create the audit runner.** Extend the existing PowerShell trace pattern or create one general runner that receives a case manifest. It must not contain case-specific facts or hardcoded output decisions.
6. **Run six source analyses.** Capture upload, extraction/OCR, classification, quality, page count, warnings, and timing. Stop and record a review blocker where source quality is insufficient.
7. **Run six complete generations.** Use the real endpoints and polling path, preserve source pages and IDs, record provider/model/fallback/retry evidence, and never synthesize missing fields.
8. **Review semantic gates.** Verify facts, parties, dates, procedural identity, legal sources, source references, section roles, placeholders, repetition, technical leakage, and final readiness. Create a red test before changing any causal implementation bug.
9. **Apply minimal generalizable repairs.** Modify the narrowest existing contract that explains the reproduced failure; never branch on a case name, filename, expediente, or person.
10. **Export both formats for each passing case.** Use guarded DOCX and PDF routes; retain binaries, manifests, hashes, page counts, extracted text, and error responses. Draft/review outputs are not counted as approved PASS cases.
11. **Render and inspect every pair.** Install or locate a supported `soffice.exe` renderer if absent, render DOCX and PDF pages, inspect first/intermediate/final pages, and rerun after every layout correction.
12. **Run regression.** Typecheck, lint, focused legal-engine tests, upload/OCR/cache integration, acceptance tests, browser E2E, six-case runner, export checks, and production build. Attribute pre-existing failures separately but do not hide failures affecting the legal flow.
13. **Generate the three reports.** Write the full Markdown report, create a readable DOCX from the report, export the PDF, render/inspect both report formats, and link every case artifact from the Markdown.
14. **Stop at legal readiness.** Report PASS only when all six cases satisfy every required gate. If a case remains `REQUIERE_REVISIÓN`, it is evidence of a correct blocker but does not count as one of six approved cases; do not falsify the summary to reach six.
15. **Defer Windows packaging.** Record the later recommendation for a single-node Windows wrapper, but do not add Electron/Tauri, installers, auto-update, code signing, or desktop IPC in this phase.
